## Review — Fleet state, telemetry, health & recovery (read-only study; no files were changed)

### 1) System understanding

Two collectors feed one append-only metric store. The gateway's `EndpointTelemetry` (endpoint-telemetry.mjs) polls each OpenAI-backend worker's native metrics every 2 s (vLLM/Tensorfold `/metrics` Prometheus text, oMLX `/api/status` + admin activity), turning cumulative counters into deltas guarded by monotonicity, 30 s adjacency, and restart epochs; the dashboard reuses gateway rows via `useShared` and additionally derives `endpoint_phase` rows (`endpointFleetSamples`). Both dashboard `FleetSpeedReader` (2 files) and `PerformanceReader` (8 files) incrementally tail daily `metrics-*.jsonl` (anchor-validated cursors) into `FleetSpeed` (windowed phase/energy aggregates; trapezoidal power with 60 s gap/scope/restart breaks, 80 % coverage before kWh extrapolation) and `PerformanceHistory` (cohort-matched self/peer slowdown lights). `HardwareTelemetry` runs push/pull adapters (SSH nvidia, mac-local, JSONL tail) into a validated numeric schema. `MonitoringHistory` persists 15-min phases/rates keyed by worker fingerprint, bridging restarts with `unknown`, never stretching downtime. `Recovery` is a durable, single-task state machine (`queued→restarting/starting/bootstrapping→verifying→recovered/verified_paused/failed/reconciliation_needed`) with ownership/hold/pause/cooldown gates, inspect-verify-readmit, and 10 k journal cap; oMLX adds a reservation/permit transaction controller. `lifecycle`/`service-control` orchestrate launchd start/stop/park with door-coordinated holds; `server-operations`/`operation-*` persist approved serving-change receipts.

### 2) Strengths

- **Data-quality discipline is exceptional.** Counter differencing is guarded everywhere: epoch checks (`endpoint-telemetry.mjs:23-24` "Only two differing, present epochs count as a restart"), plausibility bounds (`fleet-speed.mjs:89`), and duplicate rejection via content-hashed `sample_id` (`fleet-speed.mjs:83-86`). The vLLM decoding-identity rework ("an idle engine anchors the identity", `endpoint-telemetry.mjs:76-92`) is carefully reasoned and test-pinned against dropped polls and drift.
- **Honest-unknown posture.** Energy is only extrapolated at ≥80 % coverage with a single scope (`fleet-speed.mjs:179-193`), thermal-only samples explicitly "say nothing about power" (`fleet-speed.mjs:97-98`), and reader status (`waiting/catching_up/ready/unavailable`) is surfaced, not hidden.
- **Incremental file readers are robust**: identity + tail-anchor verification catches truncation/rewrite (`fleet-speed.mjs:203-206`), rotation triggers clean rebuilds, line/byte budgets everywhere.
- **Recovery never replays uncertain commands**: durable state write *before* command issue (`recovery.mjs:447` "durable BEFORE command"), lost ack → `reconciling`, `reconcile()` observes instead of re-issuing (`recovery.mjs:394-399`); reservation semantics for shared machines are tested (`recovery-omlx-controller.test.mjs:121-123`).
- **Tests pin the subtle behaviors** (127 s prefill vs scrape denominators, sub-poll prefill placement, shared-telemetry dedupe, restart history bridging with `unknown`).

### 3) Findings

1. **medium · efficiency · ds4-gateway/dashboard.mjs:454,551 + performance-lights.mjs:131-132** — Every 2 s the dashboard parses the *same* metric files twice: `polling = true; readEvents();requestHistory.poll();fleetSpeed.poll();performanceHistory.poll();ratePeaks.poll();` with `const interval = setInterval(poll, 2000)`, where `fleetSpeed=new FleetSpeedReader(runtime)` (2 files, fleet-speed.mjs:190) and `performanceHistory=new PerformanceReader(runtime,…)` (`super(directory,{retainedFiles:8,…})`) each keep independent cursors and JSON-parse every new line of the shared newest files (up to 4 MiB each). Two accumulators must stay separate (different retention/validation), but the parse work is duplicated. *Remedy:* one shared line-pump that fans parsed rows to both accumulators (or derive `FleetSpeed` rows from the Performance pass), keeping each side's validation. Effort M, low risk.

2. **medium · bug · ds4-gateway/fleet-power-service.mjs:37-41 + dashboard.mjs:529** — A single unreadable saved power receipt crashes dashboard startup: `let value=JSON.parse(fs.readFileSync(target,'utf8')); if(value.action_id+'.json'!==file||!machineGroup(value.worker)||…)throw Error('Invalid saved power receipt');` inside `createFleetPowerService`, which `runDashboard` calls unguarded. `save()` (fleet-power-service.mjs:59-62) does `fs.writeFileSync(temp,…);fs.renameSync(temp,file);` with **no fsync** (unlike `server-operations.mjs:53-63`, which fsyncs file and folder), so a power cut can plausibly leave a truncated file → JSON.parse throws → dashboard exit loop under launchd KeepAlive. Every other store in this area degrades gracefully (`MonitoringHistory` → status `'unavailable'`, `server-operations.mjs:87-89` → `'unreadable'` rows). *Remedy:* per-file try/catch; skip and surface an `'unreadable'` index entry; optionally fsync like `server-operations.write`.

3. **medium · bug (data-quality signal) · ds4-gateway/fleet-speed.mjs:226,232 with 52,56,59** — The 6 h trend silently disables for the rest of the day after any *validity* exclusion: `const partial=!!(this.malformed||this.speed.rejected||this.speed.evicted);` gates `const supported=ready&&!partial&&…`, but `rejected` also increments for benign, correctly-handled conditions — counter regression at engine restart (`fleet-speed.mjs:56`), out-of-order replay (:52), power-observation ordering (:101). The accumulator is only reset by `rebuild()` (day rotation), so one restart on an epoch-less engine pins `change_pct:null`/`trend:'insufficient'` for up to 24 h even though history is complete and readable. `fleet-speed.test.mjs:180-181` pins the *malformed* case, not the counter-reset case. *Remedy:* base `partial_history`/trend support on unreadable signals (malformed/evicted/rescans) and report validity rejections separately (they're already counted in `rejected_records`). Needs product sign-off — see open questions.

4. **medium · comment (doc drift) · docs/generation-health.md ("Operator recovery" step 4) vs ds4-gateway/gateway.mjs:2142 + generation-health.mjs:46-50** — The doc says the quarantine readmission check "uses a 32-token output budget, thinking disabled and a 20-second deadline for this check only". The implemented `Verify & readmit` path is `verifyGeneration(n.url,…,{worker:n,timeoutMs:config.request_timeout_ms})` — and `verifyGeneration` deliberately sends *no* sampling parameters (`req.end(JSON.stringify({model,stream:false,messages:[…]}))`) with the comment "Keep the backend's native output and thinking behavior" (generation-health.mjs:46-50), and the deadline is the configured request timeout (default 360000000 ms = 100 h; install.test.mjs:65). The 32-token/thinking-disabled description actually belongs to the *recovery executor's* `verifyRecovery` (recovery-verify.mjs:39, `max_tokens:32,…thinking:{type:'disabled'}`), which worker-recovery.md documents correctly. *Remedy:* rewrite that paragraph to distinguish the two verification paths (UI resume check = native settings + request deadline; executor canary = 32-token/thinking-disabled synthetic).

5. **medium · efficiency · ds4-gateway/recovery.mjs:497-500 + recovery-transport.mjs:115,143** — Automatic-recovery sweeps inspect enrolled workers *sequentially*: `for(const [id] of this.configs){…await this.inspect(id);…}`. Each attempt has `timeoutMs=45000` and `recoveryCall` tries every SSH target (`for(const target of sshTargets(config))`, up to 5), so a few unreachable workers (e.g., powered-off Sparks with 4 fallbacks) can make one `tick()` take many minutes; the `busy` guard makes later 30 s ticks skip, delaying recovery offers for *reachable* workers behind dead ones. Inspections are read-only and independent. *Remedy:* run `inspect()` concurrently with a small concurrency cap (e.g., 4), then evaluate status/requests serially as today.

6. **low · tidy · ds4-gateway/fleet-power-service.mjs:224** — Dead guard: `if(requests.has(action_id))return runTool(input);` is unreachable because the earlier `const prior=requests.get(action_id); if(prior){…return…}` block (~:209-213) already returns or throws for any in-flight action ID. Related latent gap: the fire-and-forget `.catch(error=>{request.result={…state:'unverified'};})` (:230-231) never persists a terminal receipt — the saved file stays `state:'running'` from :225, which would trigger the :77 precheck refusal ("no terminal receipt") after restart while not appearing in `unresolved_actions` (:153 filters `state==='unknown'`). Today `createPowerRunner.run` cannot reject (power-scripts.mjs catches spawn and verify errors internally), so both paths are defensive; if the runner contract ever changes, the receipt would stick as `running`. *Remedy:* delete the dead line; in the catch, `save({…,state:'unverified',receipt:{error}})` for symmetry with the success path.

7. **low · bug (error taxonomy) · ds4-gateway/recovery.mjs:373-374** — `request()` doesn't distinguish a *failed* inspection from identity drift: `const reason=this.reason(n,s,{canary,qualification})` runs with `s=observed?.value===undefined` when the latest (fresh) inspection errored, so a docker-pair worker yields `'pair_capacity_or_identity_unverified'` and others `'service_identity_or_profile_unverified'` — mislabeling "we couldn't inspect" as "identity changed", which the UI/docs treat as a durable gate. `workerStatus` (:304) and `profileHandbackOffer` (:325, `observed.error||…`) both guard this; `request()` doesn't. No crash (the docker-pair check short-circuits on `!digest(s?.pair_epoch)`), but the refusal reason misleads operators/Genie. *Remedy:* after the freshness check, `if(observed.error)throw new Error('service_inspection_failed')`.

8. **low · tidy · ds4-gateway/monitoring-history.mjs:40-43** — The moment a worker leaves the gateway roster, `sync` deletes its persisted restore copy (`…telemetry.histories.delete(id);this.loaded.delete(id);`), so a worker that flaps out/in of the roster with an unchanged fingerprint cannot restore its saved 15-min phase/rate history — the file still contains it, but the in-memory `loaded` cache was dropped. Identity changes correctly discard history (tested); roster flaps arguably shouldn't. *Remedy:* keep `loaded` entries until identity change or successful restore; they're bounded by `MAX_BYTES`.

9. **low · tidy · ds4-gateway/fleet-feature-config.mjs:5-6** — `validateGenieCapabilities` silently drops unknown keys (`if(!genieCapabilityKeys.includes(key))continue;`), inconsistent with the strict "Unsupported … setting" validation used by `hardwareTelemetryConfig` (hardware-telemetry.mjs:113-114) and `recoveryConfig` (recovery-transport.mjs:36). A typo'd capability (`'reblance'`) is ignored and the default (often `true`) applies. *Remedy:* either reject unknown keys or log them once; at minimum document the tolerance.

10. **low · efficiency (needs verification on magnitude) · ds4-gateway/performance-lights.mjs:105-121** — `PerformanceHistory.snapshot` rescans all intervals many times per call (1 prune + per-device `own` + 2 kind filters + per-kind full `peerRows` scan, each also `clip`-copying matches), and it runs on every dashboard snapshot (1 s cache, dashboard.mjs:503-505) against a documented 200 k-interval / 7-day budget. With a busy week of history and ~8 devices this is plausibly millions of iterations per second of wall time; I could not measure without executing code. *Remedy:* pre-bucket intervals by node (and by profile) once per `poll()`, or maintain per-node arrays at accept time; only the compare step needs recompute.

11. **low · refactor · ds4-gateway/recovery.mjs:404-493 vs recovery-omlx-controller.mjs:132-189** — The plain and oMLX executors duplicate the same guard skeleton — inspect → ownership/hold/admission veto → native-policy recheck → issue → poll → verify → readmit-phase ownership recheck → held-vs-recovered commit — with subtly different orderings (e.g., `requireNativePolicy(before,c)` in one, per-permit checks in the other). Both also duplicate the terminal-state constants and journal-cap checks. *Remedy:* extract a shared "recovery guard sequence" helper (ownership/admission/native-policy at `action`/`verify`/`readmit` phases) consumed by both executors; keep the different transport/verification strategies separate.

### 4) Top 5 proposals

1. **Unify the metric-file read path** behind one pump feeding both `FleetSpeed` and `PerformanceHistory` accumulators (finding 1). Effort **M**, risk low — the two validators stay, only parsing is shared. Halves steady-state telemetry CPU/IO and removes a class of drift between the two views.
2. **Recalibrate `partial_history`/trend gating** to unreadable-history signals only (finding 3). Effort **S**, risk low-medium (a documented, test-pinned behavior changes; needs a product decision). Restores the 3h-vs-3h trend after routine engine restarts.
3. **Harden mutable-store loading uniformly** ("preserve unreadable evidence") for power receipts, and add fsync-on-publish there like `server-operations` (finding 2). Effort **S**, risk low. Removes the only startup crash-loop path I found in this area.
4. **Concurrent recovery inspection sweeps** with a bounded cap (finding 5). Effort **S/M**, risk low (read-only, results evaluated serially afterwards). Makes automatic-recovery latency independent of unreachable machines.
5. **Extract the shared recovery guard sequence** across executors (finding 11). Effort **L**, risk medium — touches the safety-critical ordering of ownership/native-policy/pause checks; do it with the existing recovery tests as the net. Long-term this is the main lever against divergence as more adapters (omlx, pair, launchd bootstrap) accrete.

### 5) Open questions / disagreements

- **Finding 3 may be intended.** `fleet-speed.test.mjs:180-181` deliberately pins "one malformed line ⇒ trend insufficient", and ui/ui.js:724 says the trend "needs … complete readable history". My disagreement is narrower: *validity rejections* (counter resets, replays) are not unreadable history. If the maintainer disagrees, the remedy is a doc sentence, not code.
- **oMLX reservation persists after terminal `reconciliation_needed`** (peers stay `recovering=true` until reconcile or restart) — `recovery-omlx-controller.test.mjs:121-123` shows this is intended (a native transaction may still be running). I did not flag it, but the UI could make "this machine is fenced by action X, use Recheck" more explicit; that's a UX-area question, not a bug in my evidence.
- **`machinesFor` fallback treats each unlisted worker id as its own machine** (fleet-machines.mjs:26-27), and two different SSH aliases for the same physical box are distinct machines unless `machine_groups` is configured. Recovery docs cover this, but the same table gates `fleet-power-service` stop-refusals — a misconfigured alias pair could let a stop proceed while a sibling model serves. The real fix likely lives in enrollment tooling/doctor (config area), not here.
- **10 000-operation journal cap is documented** (worker-recovery.md "never silently deletes recovery history"), so I did not flag growth as a bug; whether terminal operations should eventually archive is a product question.
- The magnitude of finding 10 needs a measurement pass (`dashboard-overhead.test.mjs` exists); I could not run anything under the read-only mandate, and nothing else required mutation to investigate.
